# 复盘写作规范（retro-writing）

DSH 经验复盘管线（dsh-retro）配套技能：把一次会话/工程提炼成符合用户模板的复盘卡片。

## 何时使用

- 用户要求"总结 / 复盘 / 沉淀经验 / 回炉"时；
- 你调用 `retro_draft` 工具生成复盘草稿时；
- `/weekly` 周汇总与 `/retro` 复盘初稿的正文撰写。

## 铁律（用户偏好，来自其笔记原则）

1. **诚实具体**：只写会话/工程中真实发生的事实；不确定处标注"存疑"，绝不编造。
2. **用自己的语言**：复盘正文用中文、第一人称、口语化但准确；避免空话套话（"提高了效率"必须换成"把 X 从 A 改为 B，耗时从 3h 降到 40min"）。
3. **保留可复现细节**：涉及代码/命令/配置的坑，保留最小可复现片段与文件路径；涉及决策，写清"当时选了 A 而不是 B，因为……"。
4. **区分事实与推断**：现象（事实）与根因（推断）分开写；根因没有实锤时标注"疑似"。
5. **AI 不替用户拍板**：初稿必须附带"待确认问题"小节（3–8 个问题），把需要用户回忆、确认或选择的地方明确问出来，而不是自行假设。
6. **对齐模板结构**：复盘卡片遵循 experience 模板：项目目标 / 环境与栈 / 关键过程 / 踩坑与根因（现象-根因-修复）/ 关键经验 / 行动项 / 参考链接。
7. **可迁移性优先**："关键经验"一节只写能复用到下一个工程的内容（通用结论、模式、反模式），项目专属细节放"关键过程"。
8. **周汇总**：本周三件事（用户模板）/ 推进情况 / 踩坑 / 可复用经验 / 待审草稿与发布队列 / 进化建议，逐条可勾选 keep/merge/discard。

## 输出格式

复盘卡片正文为 Markdown，头部 frontmatter 由插件生成，正文按上述结构；"待确认问题"放在文末 `---` 分隔线之后。
